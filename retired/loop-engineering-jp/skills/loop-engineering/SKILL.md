# loop-engineering — 改善ループの設計規範（正本）

AIの完了報告は、実際にやったことではなく「期待されている報告」に引き寄せられる。
実例がある。Codex に実装を任せた運用で、「構文チェック済み」という完了報告の裏で、チェックは一度も実行されていなかった。発覚したのは、夜間の自動処理が全滅した朝だった。

この規範は、報告を信用しなくても品質が出る構造を作るためのもの。**改善ループ**（直す→採点→直す）の回し方と、それを支える**ハーネス**（テスト・関門・点検表など、モデルの外側に組む検査一式）の据え付け手順を定める。

## 背骨の3規律

1. **失格条件は、採点と分ける。** 合計点や適合数だけでループを回すと、構造的な穴が開く——「他の項目が全部OKなら、目的を壊す欠陥が1つあっても通過する」。だから「採点結果に関係なく不合格」の失格条件（目的を壊す変更・過去に踏んだ地雷）を、採点とは別の関門として持つ。
2. **機械の検査を先に厚く、AIの採点は後に薄く。** 決定論的で速い機械検査（テスト・ビルド・変異確認）を先に全部通し、遅くて曖昧なAI採点は、機械で測れないもの（見た目・意味）だけに使う。そして**採点は必ず生成役と別のエージェントに出す**。自分の成果物を評価させると、出来が凡庸でも自信満々に褒める。冒頭の水増し報告も、生成役の自己採点も、同じ構造から起きる。
3. **部品は増やさず、削る。** 点検が重くなると素通しされ、ハーネス全体が死ぬ。目安は機械的5個・推論的1個。超えたら足すのではなく差し替え、点検のたびに「モデルが賢くなって不要になった部品はないか」を1問だけ問う。

## 語彙（4象限）

| | 機械的（決定論的・速い・確実） | 推論的（LLM判定・遅い・曖昧） |
|---|---|---|
| **先回りの手引き**（行動する前に方向づける） | 型定義・書式の自動整形・権限の拒否リスト | CLAUDE.md・DESIGN.md・参照資料 |
| **事後の点検**（行動した後に観測させ自己修正させる） | テスト・ビルド・リンター・変異確認・表示速度計測 | 別エージェントによる採点・見た目のスクショ採点 |

## 改善ループの回し方

**回す前に、北極星を文書化する。** 北極星＝満点の姿を定めた仕様（ページの仕事・参照水準・トーン・捨てるもの。置き場は DESIGN.md 等）。ループは北極星に収束させる装置であって、仕様を発明する装置ではない。観点と配点だけ決めて回すと、採点役が毎周それぞれの理想像を発明して減点し、点数が頭打ちになる（実測: 4周で41→64点止まり・採点役同士が真逆の指摘で振動）。北極星が無いなら、オーナーへの質問攻めで固めるのが第0周。

推論的な点検は1回の合否で終えず、**全適合に達するまで「直す→採点→直す」を回す**。

1. 生成役が直す → 機械的点検を全部通す（赤ならこの先へ進まない）。**1周の変更は小さく刻む**——大玉の一括改修は新しい退行を持ち込み、次の周が丸ごと後始末に消える（実測: 一括改修の周で64→57点へ逆走）
2. 採点役（生成役と別のエージェント）が**北極星との適合チェックリスト**で全項目OK/NG＋指摘リスト。指示は「褒めるな・粗を探せ」。渡すのは北極星と**未解消の指摘・前周までに直した点（退行の確認用）**——前周の点数は渡さない（前の数字を見せると、採点がその値に引きずられる）
3. 不適合が残るなら直して1へ戻る

決まりごと（具体値は各リポジトリの `.claude/harness.md` に書く）:

- **合否は適合チェックリストで測る（周回中は固定）**。100点採点を併用するなら傾向を見る参考値に格下げする——粗探し指示の採点役はどんな状態でも粗を10件出すので、「85点で合格」のような絶対閾値には構造的に届かない
- **採点役同士が振動したら統括が裁定する**: 周をまたいで真逆の指摘が出たら（例: グラフの軸起点を巡る往復）、従わずに設計を確定して固定し、以後その論点は採点対象から外す
- **失格条件を採点と分ける**（背骨の規律1）
- **停止条件は3つ組**: チェックリスト全適合＋公開ブロッカーゼロ（到達は停止の合図であって品質の証明ではない）／周回上限（目安3〜4周）／連続停滞（適合数が2周増えない＝小手先でなく設計の問題。人間の判断へ）
- **ループを抜けても、人間の承認なしに公開しない**（点検だけの無監督運用は技術的負債を複利で増やす）

## 手順A —「ループを回したい」「ハーネスを組みたい」と言われたら

1. **棚卸し**（対象リポジトリで実測する。推測しない）
   - テストは在るか・実際に通るか／公開前の関門は在るか／`CLAUDE.md` は現況と合っているか／`.claude/harness.md` は在るか
2. **弱い象限を特定**する。4象限のどこが空か。たいてい「事後×推論的（見た目・意味の点検）」が空。
3. **部品を1〜3個だけ提案**する（下記カタログから）。多く積まない＝重い点検は素通しされる。
4. オーナー承認後に実装する。実装を別のAIに委任する体制なら、**検収と採否は必ず発注側が握る**（冒頭の実例のとおり、完了報告は検証の入力にしない）。1ファイル程度なら直接書いてよい。
5. `.claude/harness.md` が既にあるなら、新設ではなく**その改訂**として扱う。

### 部品カタログ（既存資産のみ）

| 部品 | 象限 | 中身 |
|---|---|---|
| そのリポジトリのテスト | 事後×機械 | 既存のテスト一式。無ければ作るのが最優先 |
| 公開前の関門 | 事後×機械 | 「全パスしないと公開しない」の明文化（例: `npm test` 全パスを公開の条件にする） |
| 変異確認 | 事後×機械 | 直した行をわざと戻し、テストが落ちるか確かめる。テストの効き目自体を測る |
| 別エージェントによる採点 | 事後×推論 | 生成役と別のエージェントに受け入れ基準で採点させる。公開前は必須 |
| ブラウザ自動操作で見た目の採点 | 事後×推論 | 実際にページを開き・操作し・スクショを撮ってから採点する（Playwright 等）。ウェブ案件の要 |
| `CLAUDE.md` の整備 | 先回り×推論 | 地雷と正本ポインタ。**1項目1行**に圧縮 |
| `DESIGN.md` の整備 | 先回り×推論 | 配色・書体・余白の値＋なぜそうしたかの散文。見た目のブレを先回りで止める |

## 手順B —「このプロジェクトはループ運用でいく」と宣言されたら

宣言されたら、そのリポジトリに以下を据え付けて commit する。以後、**宣言は不要**。

1. 手順Aの1〜2（棚卸しと弱点特定）を先に行う。
2. **`.claude/harness.md` を新設**（下記テンプレ）。git管理＝PCが変わっても効く。
3. **そのリポジトリの `CLAUDE.md` に1行だけ追記**する。定型文:

   ```
   - **改善ループ運用中**: 変更後は `.claude/harness.md` の点検表に従う（公開前の判断を伴う点検は必ず別エージェント）
   ```

4. コミットする（例: `loop: 点検表を新設しCLAUDE.mdへ配線`）。

### `.claude/harness.md` テンプレ

```markdown
# ハーネス点検表（<プロジェクト名>）

宣言日: YYYY-MM-DD

## 変更後に回す（機械的・上限5個の目安）

- [ ] <コマンド> — <何を守るか>

## 公開前に回す（推論的・1個の目安）

- [ ] 改善ループを回す（採点役=生成役と別のエージェント・**このセッション自身で採点しない**）
      北極星: <満点の姿を定めた仕様文書へのポインタ。無ければループの前に固める>
      適合チェックリスト（北極星から起こす・周回中は固定）:
      - <仕様の要求>: OK/NG — <適合の条件>
      停止条件: 全適合＋公開ブロッカーゼロ／<N>周上限／<M>周連続で適合数が増えない→オーナー判断
      失格条件（適合数に関係なく不合格）: <このプロジェクトの目的を壊す変更・過去に踏んだ地雷>
- [ ] 見た目の変更を含むならブラウザ自動操作（またはプレビュー）で実際に開いて撮ってから採点役へ渡す

## 毎回1問：削るものはないか

- [ ] 上の部品のうち、モデルが賢くなって不要になったものは？ あれば撤去を提案する
```

**上限の目安＝機械的5個・推論的1個**（背骨の規律3）。

## 落とし穴

- **点検表の肥大** — 兆候は「点検が面倒で素通しされたコミット」。上限と「削る1問」が防波堤。
- **自己採点への回帰** — 実装したセッションが自分で「点検表OK」と申告する。冒頭の水増し報告と同型で、悪意なしに起きる。判断を伴う点検は必ず別エージェント。
- **規律は機械強制ではない** — 手順Bは `CLAUDE.md` 経由の規律で効く。**実際に破られた項目が出たら**、その項目だけフック（settings.json）で機械強制に格上げする。破られる前にフックを足さない（使い慣れない機構を先回りで増やすと、それ自体が事故源になる）。
